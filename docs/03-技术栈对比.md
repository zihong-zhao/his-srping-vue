## 1. 结论摘要

**推荐：Spring Boot 3.x + Java 21 单一主栈；Python 只做离线脚本，不作为运行时服务。**

针对已确认的"1 人 + 三级医院 + 电子病历 4 级 + 本地机房"，理由如下：

1. **领域生态决定评级能否落地**：医保接口、CA 电子签名、HL7、院内既有 LIS/PACS 厂商，Java SDK 与接口文档占绝对多数；
2. **单人项目最大的敌人是"半年后改不动"**：强类型 + IDE 重构 + 编译期检查，显著降低一个人维护 50+ 张表、16 个模块的认知负担；
3. **双栈是负资产**：单人维护两套运行时没有收益，Python 只保留离线脚本形态，不引入第二个服务进程；
4. **性能不是选型依据**：本项目峰值 30–80 TPS，Java 与 Python 都富余，瓶颈在数据库与医保接口。

> 如果你的 Python 熟练度显著高于 Java（例如 Java 只写过 Demo），则改选 FastAPI 主栈，但必须按第 6 节补齐工程能力——这不是"难度"问题，而是"一个人能否长期维护"的问题。

## 2. 对比对象与版本基线

| 方案 | 组成 | 定位 |
| --- | --- | --- |
| **A. Spring Boot** | Java 21 (LTS) + Spring Boot 3.3/3.4 + Spring Security + MyBatis(-Plus) + Flyway + Redis + RabbitMQ | 企业级、强类型、长生命周期系统的主流选择 |
| **B. FastAPI** | Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2.0 + Alembic + Celery + Redis | 异步高性能 API，现代 Python 工程化首选 |
| **C. Django** | Python 3.12 + Django 5 + DRF + ORM/Migrations + 内置 Admin | 全栈快速交付、内置后台管理，适合中小系统 |

> Flask 不在同一量级（缺乏 ORM/迁移/权限的标准化方案），不纳入正式对比，只在脚本工具层使用。

## 3. 逐维度对比

### 3.1 语言与工程质量

| 维度 | Spring Boot | FastAPI | Django |
| --- | --- | --- | --- |
| 类型系统 | 编译期强类型，重构安全 | 运行期为主，Pydantic 提供入口校验（非全链路） | 弱类型，靠测试与约定 |
| 大项目可维护性 | 强，IDE 重构/跳转可靠，适合 10 万行以上 | 中，需严格分层约定（routers/services/repositories） | 中，Django 约定帮助大，但大项目易散 |
| 依赖管理 | Maven/Gradle，锁定版本成熟 | uv/poetry，近年已明显改善 | 同左 |
| 数据库迁移 | Flyway / Liquibase | Alembic（需手写较多） | 内置 migrations，最省心 |
| 测试基建 | JUnit5 + Testcontainers | pytest + testcontainers-python | Django TestCase |

### 3.2 并发与性能

| 维度 | Spring Boot | FastAPI | Django |
| --- | --- | --- | --- |
| 并发模型 | 线程池；Java 21 虚拟线程可承载大量阻塞 IO | asyncio 单线程事件循环（CPU 密集受 GIL 限制） | 同步 WSGI，靠多进程/多线程 |
| 典型 QPS（简单查询，单实例 4C8G） | 1500–3000 | 1000–2000（异步 + 异步 DB 驱动） | 300–800 |
| HIS 场景是否够用 | 富余 | 够用（本项目峰值 ~150 TPS） | 够用（中小规模） |
| 冷启动 | 3–8 s | <1 s | 1–2 s |
| 单实例内存 | 300–600 MB | 80–200 MB | 150–300 MB |
| 长时运行稳定性 | JIT 预热后非常稳定，GC 可调 | 稳定，但需注意内存泄漏与阻塞调用 | 稳定 |

**关键结论**：本项目峰值收费类交易约 50–120 TPS，三者在性能上都**不是瓶颈**。真正的瓶颈是数据库与外部医保接口，语言层选型不应以性能为主要依据。

### 3.3 事务与资金/库存一致性

| 维度 | Spring Boot | FastAPI | Django |
| --- | --- | --- | --- |
| 声明式事务 | `@Transactional`，传播行为/隔离级别完善 | 需显式 `with session.begin()`，更易漏写 | `transaction.atomic`，语义清晰 |
| 乐观锁/悲观锁 | JPA `@Version` / MyBatis 手写，生态成熟 | 手写 | 手写 |
| 事务内事件（Outbox） | 成熟实践多，可与事务同步提交 | 可做，需自建 | 可做 |
| 资金场景工程经验 | 国内金融/医疗大量案例 | 相对少 | 少 |

三项都能做到正确，但 **Java 侧的"防错"能力更强**（编译期约束 + 成熟的事务模板），而 Python 更依赖团队纪律与代码评审。

### 3.4 医疗行业生态（本项权重最高）

| 能力 | Spring Boot | Python | 说明 |
| --- | --- | --- | --- |
| 医保接口 | 强 | 中偏弱 | 各地医保 SDK/加解密组件以 Java/.NET 为主，Python 往往需自行实现签名、报文解析 |
| HL7 v2 / FHIR | HAPI 等成熟库 | 有 `hl7apy`、`fhir.resources`，可用但案例少 | HIS 互联互通测评常用 HL7 |
| DICOM | dcm4che（成熟） | pydicom（成熟，偏影像处理） | RIS/PACS 集成两者都行 |
| CA 电子签名 | 各家厂商提供 Java SDK | 多为 C/S 控件或 HTTP 服务，语言无关 | 建议统一走签名服务 HTTP 接口，两边都能接 |
| 医院现有系统集成 | 主流 HIS/EMR 厂商均为 Java | 少 | 接口对接时改造参考更少 |
| 报表与 BI | 一般（需自研或接 BI 工具） | **强**（pandas/polars/openpyxl） | Python 明显优势 |
| AI/大模型应用 | 需通过服务调用 | **强**（生态直接可用） | CDSS、病历质控、OCR |

### 3.5 人才与运维

| 维度 | Spring Boot | Python |
| --- | --- | --- |
| 国内医疗 IT 人才存量 | 高（HIS 厂商主流技术栈） | 低（偏互联网/数据方向） |
| 招聘与交接成本 | 低 | 中 |
| 医院信息科理解度 | 高（能看懂部署文档、找得到人） | 中 |
| 运维复杂度 | 中（JVM 参数、日志体系） | 低（部署简单） |
| 信创兼容 | 好（东方通、金蝶天燕等国产中间件对 Java 支持完善） | 一般 |

### 3.6 开发效率（客观看待）

- **首个可演示版本**：FastAPI ≈ Django > Spring Boot（Python 少样板代码，迭代快 20–40%）。
- **第 6 个月之后**：差距迅速缩小甚至反转。HIS 有 50+ 张核心表、16 个模块，Java 的重构安全与静态检查在大规模修改时收益明显。
- **"Python 开发快"的真相**：快在原型与脚本，慢在长期维护与类型缺失带来的隐性 bug。

## 5. 推荐方案：Java 主栈 + Python 离线脚本

### 5.1 技术栈明细（主栈）

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 运行时 | Java 21 LTS（启用虚拟线程） | LTS 支持周期长，虚拟线程缓解阻塞 IO |
| 框架 | Spring Boot 3.4 | 生态最稳，团队易招人 |
| Web | Spring MVC + Bean Validation | 契约清晰 |
| 持久层 | **MyBatis-Plus + 手写复杂 SQL** | HIS 有大量复杂报表与多表联查，JPA 全自动反而难调优 |
| 事务 | Spring `@Transactional` + 显式隔离级别 | 收费/库存必须可控 |
| 迁移 | Flyway | 版本化、可审计 |
| 认证 | Spring Security + JWT（可扩展 OAuth2/SSO） | 与医院 AD/LDAP/统一身份对接 |
| 缓存/锁 | Redis + Redisson | 号源、字典、分布式锁 |
| 消息 | RabbitMQ（或 Kafka，若需事件回溯） | Outbox 事件派发、异步任务 |
| 文档 | springdoc-openapi | 接口契约先行 |
| 测试 | JUnit5 + Testcontainers | 集成测试跑真实 PG |
| 构建 | Maven | 团队通用 |

### 5.2 离线脚本（Python，按需使用，不参与运行时）

| 场景 | 形态 | 说明 |
| --- | --- | --- |
| 复杂报表导出 / 数据加工 | 离线脚本（定时或手动触发） | 只读从库，生成文件写入对象存储 |
| 医保对账差异分析 | 离线脚本 | 结果以文件或管理端导入回写，不常驻服务 |
| 数据迁移与校验 | 一次性脚本 | 严格执行患者数/金额/库存三方对平 |
| 病历质控 / CDSS / 智能助手 | **4 级不要求，评级后再评估** | 如引入，用独立服务，故障不影响临床 |

> 单人团队不在生产环境跑常驻 Python 服务：多一个进程就多一套依赖、日志、监控与升级维护。

> 旁路服务的硬约束：**只读不写主业务表**（对账结果除外且需幂等）；不参与收费/医嘱/发药主链路，故障不影响临床。

## 6. 若采用 Python 主栈的适配方案

### 6.1 选型

| 场景 | 建议 |
| --- | --- |
| 需要快速交付 + 强后台管理（主数据、字典维护多） | **Django 5 + DRF**（内置 Admin 能省掉大量管理界面） |
| 接口密集、需高并发、前后端分离彻底 | **FastAPI + SQLAlchemy 2.0（async）+ Alembic + Pydantic v2** |
| 本项目推荐 | **FastAPI**（模块化单体 + 明确分层：`api / service / repository / domain`） |

### 6.2 必须补齐的工程能力（否则会在 6 个月后反噬）

1. **全链路类型**：`mypy --strict` 纳入 CI，Pydantic 模型覆盖所有出入口。
2. **事务模板化**：统一 `unit_of_work` 上下文，禁止在 router 层散写事务；资金类接口强制走模板。
3. **幂等与防重**：统一幂等中间件（`Idempotency-Key` + Redis 去重 + DB 唯一索引兜底）。
4. **审计切面**：AOP 式的装饰器统一埋点，禁止逐接口手写。
5. **多进程一致性**：定时任务必须单实例（独立 worker），或用分布式锁，避免多 worker 重复执行。
6. **复杂 SQL 能力**：报表用原生 SQL + SQLAlchemy Core，不要硬套 ORM。
7. **医保接口自研**：预留 2–4 周专门做签名、加解密、报文适配，并做联调沙箱。
8. **性能基线**：压测脚本纳入 CI，先证明 150 TPS 达标再扩模块。
9. **文档与交接**：核心模块必须有设计文档、ADR 与运维手册，避免知识只存在一个人脑中。

## 7. 决策树

```
Java 与 Python 都会，谁更熟？
├─ Java 熟练度 ≥ Python → Spring Boot 单一主栈（本方案推荐）
└─ Python 熟练度显著更高
    ├─ 仍要过 4 级评价 → 用 FastAPI，但必须按第 6 节全部补齐，并接受医保/CA 联调风险
    └─ 只做中小医院门诊收费 → FastAPI 更划算
```

单人团队的额外硬约束：**只选一个运行时**，另一门语言只用于离线脚本。

## 8. 常见争议澄清

| 争议 | 事实 |
| --- | --- |
| "Python 性能不行" | 本项目 150 TPS 级别，FastAPI 富余；瓶颈在 DB 与医保接口，不在语言 |
| "Java 开发太慢" | 首版慢 20–40%，但 16 个模块、50+ 表规模下，重构安全带来的收益会反超 |
| "Python 也能做医疗" | 能做，但医保 SDK/厂商接口文档以 Java 居多，隐性成本高 |
| "微服务才先进" | HIS 的跨模块事务极多，微服务会显著增加账不平风险，见 `01-架构方案.md` 第 3 节 |
| "选 Java 就不用 Python" | 恰恰相反：报表、AI、数据迁移用 Python 效率更高，旁路接入即可 |

## 9. 已确认决策与剩余问题

**已确认**：1 人团队、Java/Python 都会、三级医院、电子病历 4 级、本地机房、自研核心闭环、不强制信创、本地医保统筹区、LIS/PACS 厂商未定、上线即迎评。

**结论**：Spring Boot 3 + Java 21 单一主栈；Python 仅离线脚本。

上述新前提对结论的影响：

| 前提 | 对技术栈的影响 |
| --- | --- |
| 不强制信创 | 无需限制在国产中间件生态，Spring Boot 的选型约束更少，结论更稳 |
| 本地医保统筹区 | 医保接口需自研适配，但只对一个统筹区，工作量可控；Java 的报文/加解密处理更成熟 |
| LIS/PACS 厂商未定 | 必须做 IntegrationPort + Mock，Java 侧接口抽象与适配器模式更易落地 |
| 上线即迎评 | 没有"上线后再补"的缓冲，首版必须功能齐备；这提高了强类型与可维护性的权重 |

**仍需确认**：
1. 你对 Spring Boot 的实际项目经验（是否独立交付过生产系统）？若有明显短板，则改选 FastAPI 并执行第 6 节。
2. 本地医保局是否提供 Java SDK/HTTP 接口，还是只有报文规范文档？
3. 是否接受放弃 Elasticsearch / Kafka / K8s 的精简部署（单人维护必需）？
