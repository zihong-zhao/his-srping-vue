## 1. 结论摘要

**已确认不强制信创，故锁定 PostgreSQL 16**，不走国产数据库分支。

| 场景 | 推荐 |
| --- | --- |
| **默认推荐（自建/非信创）** | **PostgreSQL 16/17** |
| 团队 MySQL 运维经验深厚、已有 MySQL 体系 | MySQL 8.0.36 LTS |
| 医院强制信创 | **人大金仓 KingbaseES V9**（PG 内核，迁移成本最低）；Oracle 兼容诉求强则达梦 DM8 |
| 医院已有 Oracle 体系且预算充足 | Oracle 19c（不新建则不建议） |
| 单院 800 床以内 | **不需要分库分表**，按时间分区即可 |

**核心理由（PostgreSQL）**：
1. 复杂报表 SQL 能力（窗口函数、CTE、递归、并行查询）显著强于 MySQL，HIS 报表是刚需；
2. `JSONB` 适合存放结构化病历的扩展段、医保原始报文、可配置字段，且可建 GIN 索引；
3. 原生**行级安全（RLS）**可作为数据权限的最后一道兜底（科室/病区隔离）；
4. 部分索引/表达式索引可直接优化 `deleted = false` 这类高频条件；
5. 无许可成本，PITR（时间点恢复）成熟，社区与云厂商支持完善。

## 3. 维度对比

### 3.1 核心能力

| 维度 | PostgreSQL | MySQL 8.0 | Oracle 19c | KingbaseES V9 | 达梦 DM8 |
| --- | --- | --- | --- | --- | --- |
| 事务/隔离级别 | RC/RR/Serializable，实现严谨 | RC/RR，RR 有间隙锁差异 | 最完善 | 同 PG | 接近 Oracle |

| JSON | JSONB（可索引、可查询） | JSON（8.0.17+ 多值索引，能力弱于 JSONB） | JSON 类型 | 兼容 JSONB | 支持 |

### 3.3 HIS 场景匹配度

| HIS 特征 | 影响 | 最匹配 |
| --- | --- | --- |
| 报表复杂（月度收入、药占比、DRG 分组） | 需强 SQL、并行、物化视图 | PostgreSQL / Oracle |
| 资金类强事务（收费、退费、库存） | 需可靠事务与锁 | PostgreSQL / Oracle / MySQL |
| 结构化病历扩展字段 | 需灵活 schema | PostgreSQL（JSONB） |
| 数据权限（科室/病区隔离） | 需行级安全兜底 | PostgreSQL（RLS） |
| 海量明细（费用明细、日志） | 需分区 + 归档 | PostgreSQL 分区表 |
| 等保审计 | 需审计扩展 | PostgreSQL（pgaudit）或应用层审计 |
| 医院运维能力有限 | 需方案简单、有人会 | MySQL 略优 |

## 4. 容量估算与分区策略

### 4.1 估算（按日门诊 4,000 人次、400 床、5 年）

| 表 | 年增量（估算） | 5 年累计 | 处理策略 |
| --- | --- | --- | --- |
| `registration`（挂号） | 150 万 | 750 万 | 按年分区 |
| `bill_item`（费用明细） | 450 万 | 2,250 万 | **按年分区** + 历史归档 |
| `payment` / `refund` | 160 万 | 800 万 | 按年分区 |
| `medical_order` / 执行记录 | 250 万 | 1,250 万 | 按年分区 |
| `lab_result` 明细项 | 600 万 | 3,000 万 | 按年分区，冷数据归档 |
| `audit_log` | 1,200 万 | 6,000 万 | **按月分区**，保留 6–12 个月热数据 |
| `outbox_event` | 300 万 | 1,500 万 | 按月分区，消费后定期清理 |

**结论**：单库 PostgreSQL 可稳定承载（亿级行以内，配合分区与归档），**无需分库分表**。分库分表会破坏跨模块事务，属于负优化。

### 4.2 分区与归档

- 明细类大表（费用、医嘱、检验、日志）按**年**分区，日志类按**月**分区；
- 在线保留：业务明细 3 年热 + 2 年温；审计日志 6–12 个月（等保要求 ≥6 个月）；
- 归档：把 3 年以上冷数据导出为只读归档库/Parquet 文件，保留查询入口（按需回迁）；
- 病历正文按法规保留 15–30 年，**不归档删除**，只做存储介质分层。

## 5. 辅助存储选型（数据层整体）

| 用途 | 选型 | 理由 |
| --- | --- | --- |
| 主数据库 | PostgreSQL 16 | 见第 1 节 |
| 只读从库（报表） | PostgreSQL 流复制从库 | 报表不拖慢收费主库 |
| 缓存 / 会话 / 分布式锁 | Redis 7（哨兵或集群） | 号源、字典、幂等键、发药锁 |
| 对象存储 | MinIO（本地）/ 云 OSS | 病历附件、报告 PDF、导出的报表；**不进数据库** |
| 消息队列 | RabbitMQ（单节点） | Outbox 事件、异步任务、对账；单人运维不引入 Kafka |
| 全文检索 | 暂不引入，用 PG 内置 `tsvector` | 当前检索需求弱，多一个组件就多一份运维 |
| 数据仓库（后期） | 从库 + Parquet/DuckDB 离线分析 | 报表确实成为瓶颈时再引入 |

**单人运维精简原则**：
- 生产环境只跑 6 类进程：应用（2 实例）、PostgreSQL（主 + 从）、Redis、MinIO、RabbitMQ；
- 不引入 Elasticsearch / Kafka / K8s / 独立配置中心；
- 部署用 Docker Compose，脚本化一键拉起，并附一页运维手册（启停、备份、恢复、切主）。

**明确不做**：
- 不把影像/PDF 存进数据库 BLOB（备份膨胀、恢复变慢）；
- 不引入 Redis 当"唯一数据源"（号源必须落库，Redis 只做预扣与加速）；
- 不用 MongoDB 做主业务库（HIS 需要强事务与关系约束）。

## 6. 表设计规范（与选型配套）

1. **主键**：`bigint` 自增或雪花 ID；业务单号（挂号号、住院号、发票号）单独字段并加唯一索引。
2. **金额**：`numeric(14,2)`，**禁止 float/double**；比率用 `numeric(8,4)`。
3. **时间**：统一 `timestamptz`，存 UTC，展示按院区时区。
4. **乐观锁**：业务表带 `version int`，更新时 `where id=? and version=?`。
5. **逻辑删除**：`deleted boolean default false`，配合**部分索引** `where deleted = false`。物理删除仅限无引用关系的数据。
6. **审计字段**：`created_by / created_at / updated_by / updated_at` 全表必备，由框架统一切面填充。
7. **快照字段**：单据表冗余 `patient_name`、`dept_name`、`price_snapshot`，保证历史可读。
8. **外键**：核心主数据使用外键约束（防脏数据）；高频写入的明细表可只做应用层校验（避免锁竞争），需评审决定。
9. **索引**：按查询模式建索引，禁止无脑全字段索引；每张表索引 ≤ 5 个为宜，定期用 `pg_stat_statements` 复核。
10. **命名**：表名小写下划线、单数；索引 `idx_{table}_{cols}`；唯一索引 `uk_{table}_{cols}`。

## 7. 高可用与备份

| 项目 | 方案 | 目标 |
| --- | --- | --- |
| 高可用 | 主库 + 1 异步从库，流复制 + 脚本化手动切主 | RTO ≤ 30 min |
| 备份 | 每日全量（pgBackRest）+ 持续 WAL 归档 | RPO ≤ 15 min |
| 恢复演练 | 每季度一次，从备份拉起并校验数据量/金额 | 验证备份"可恢复"，而不只是"有备份" |
| 异地副本 | 每周全量副本送至离线介质/异地 | 防机房级灾难 |
| 升级 | 小版本滚动升级；大版本（如 16→17）先在从库演练 | 不影响业务窗口 |

## 8. 信创替代路径（本项目不启用，仅作备选）

> 本项目已确认不强制信创，按 PostgreSQL 16 实施。以下内容仅作为未来政策变化时的预案，不影响当前实施。

| 场景 | 推荐 | 迁移要点 |
| --- | --- | --- |
| 已有/新建均可 | **KingbaseES V9** | PG 内核，SQL 兼容度高；只需替换驱动与少量扩展（如 pgaudit 换成厂商审计） |
| 医院强制 Oracle 语法兼容 | 达梦 DM8 | 需处理 `serial`、`jsonb`、部分函数差异，工作量约 2–4 周 |
| 华为生态 | openGauss | 兼容 PG 但生态较窄，需厂商支持 |

**工程建议**：从第一天就避免 PG 专有语法（如 `DISTINCT ON`、自定义聚合），SQL 保持标准；分区、JSON 字段访问封装在 Repository 层，替换成本可控。

## 9. 已确认决策与剩余问题

**已确认**：本地机房、单院、300–500 床、日门诊 2,000–5,000、1 人运维、不强制信创。

**结论**：PostgreSQL 16 单库 + 主从，按年/月分区，不引入分布式数据库，不进入信创分支。

**仍需确认**：
1. 医院现有备份介质与机房条件（是否有独立备份存储、能否做异地副本）？
2. 院内是否有 Oracle/MySQL 运维人员可复用，还是完全由你一人负责？
3. 若后续政策要求信创，是否接受"金仓 KingbaseES 优先"的迁移路线？
